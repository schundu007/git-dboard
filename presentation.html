The largest single category of user reports. Installation fails and tells the user it succeeded — so they don't know where to start.
1. The build spends 1–2 hours on GPU hardware, then fails to save its output
The automated build runs for up to two hours on expensive compute. At the very last step — storing the result — the system's access credentials have expired. The entire run is discarded. There is no retry, so a brief network hiccup has the same outcome. This is the root cause of 96% of all pipeline failures and the reason the nightly check has been at 0% for 14 days.
3. Expensive GPU machines run for documentation edits and immediately do nothing
Every contribution — whether someone fixed a typo in a tutorial or rewrote a physics algorithm — triggers the same full GPU pipeline. 32 of the 100 pending changes are documentation-only. Of the 33 automated checks that fire for each one, 70% complete instantly with a "skip" result. A simple pre-check could eliminate this cost entirely.
2. Installation fails for 1 in 3 users — and reports success when it does
Two components in the software demand incompatible versions of the same dependency. This causes installation to fail, but the installer exits with a "success" status anyway. Users spend hours debugging a problem that is not their code. 49 open complaints describe exactly this. Three pending fixes are written and waiting — they just haven't been approved for release.
4. The RTX 5090 — NVIDIA's 2025 flagship GPU — crashes immediately on launch
IsaacLab has not been updated to support Blackwell-generation GPUs (RTX 5090, RTX 5070 Ti), which were released in early 2025. Users on current-generation hardware hit a crash the moment they try to run a simulation. This is the most-discussed issue in the entire tracker, and there is nothing in progress to address it.

Improvement Roadmap
A Practical Three-Phase Plan — Starting This Week
Phase 1 alone resolves most of the immediate pain. Each phase is independent and delivers measurable results on its own.
The Roadmap
1
Stop the Bleeding — Restore the Pipeline and Fix Installation
Weeks 1–3 · Builds: 16% → ~96% · Nightly: 0% → 100% · All 49 install complaints resolved
Fix the credential expiry. The build's access keys need to stay valid for the full duration of the job. Adding a retry means a single network moment no longer discards two hours of compute.
Restore the nightly schedule. A deprecated configuration setting is stopping the overnight quality check from running. A one-line fix brings it back immediately.
Create a single version rulebook. One authoritative list of which version each component requires eliminates the conflicting requirements that cause installation to fail.
Make installation failures visible. When setup fails, it should say so clearly and explain why — not exit with a false success message.
Approve the three pending install fixes. These are already written and reviewed. They are waiting only for a maintainer to approve and merge them. Doing so closes all 49 open installation complaints.
2
Reduce Waste — Spend Compute Budget Only Where It Adds Value
Weeks 4–8 · ~60% reduction in GPU spend on code reviews · ~40 GPU-hours saved per week
Check what type of change it is before spending. Documentation and text edits get a lightweight validation. Code changes get the full GPU pipeline. This alone eliminates the 32% of compute spend that currently goes to document reviews.
Build the base software once per night — not 12 times. Currently the system rebuilds the same foundation from scratch for each of 12 test configurations. Build it once and share the result across all configurations.
Cache downloads between builds. The same packages are re-downloaded from the internet on every single build. Storing them locally between runs saves approximately 18 minutes per build at no ongoing cost.
Set an expiry on failed build outputs. Two weeks of failed builds are sitting in cloud storage with no cleanup policy. A 30-day expiry removes them automatically and saves $50–200 per month in storage fees.
3
Lead the Field — Current Hardware Support and Long-Term Quality
Weeks 9–14 · RTX 5090 / Blackwell fully supported · Isaac Sim 6.0 complete · Elite delivery performance
Support RTX 5090 and Blackwell GPUs. Update the simulator to compile for NVIDIA's 2025 hardware. This is a 1–2 day code change that unblocks every user on current-generation hardware and closes the most-discussed issue in the tracker.
Complete the Isaac Sim 6.0 migration. 35% of current complaints reference version 6.0 compatibility. Finishing the migration closes a large cluster of open issues and brings the platform fully up to date with NVIDIA's simulator platform.
Fix the physics data accuracy bug. A known defect causes robot training algorithms to receive incorrect velocity data without any warning. Researchers may be training on flawed results without realising the simulator is the source of the problem.
Add automated failure alerting. The 14-day outage was discovered manually. Adding a simple alert when the quality check fails two nights in a row means the team knows within hours — not weeks.
Phase 1 requires no architectural changes — configuration and credential updates only
